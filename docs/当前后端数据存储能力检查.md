# 当前后端数据存储能力检查

> 检查日期：2026-09-05  
> 检查对象：`src/software_quality_agent/store.py`、`schemas.py`、`agents.py`、`service.py`、`server.py`  
> 对照数据：ARTA、SAFA/Dronology V0—V1、LiSSA SMOS、Irrelevant Requirements

## 1. 结论

当前后端可以保存：

- 项目基本信息；
- 一份制品的类型、名称、路径、一个版本字符串、文本正文和任意 JSON 元数据；
- 两个**整份制品**之间的关系类型、一个浮点置信度和一段文本证据；
- 对话、Markdown 报告及通用审计事件。

当前后端不能无损保存本次数据集真正需要的信息：

- 数据集身份、版本、来源提交、许可、哈希和拆分；
- 文档条目、需求、代码类/方法、测试步骤等细粒度单元；
- 人工标注、标注者、标签体系、分歧与裁决；
- “金标准链接、模型候选链接、已确认链接、拒绝链接”的区别；
- 多版本制品及关系的有效期、变更、删除和替代；
- 构建/测试/静态分析运行、结构化证据、指标和 finding；
- 二进制文件内容、MIME、大小、校验值和原文下载接口。

因此，现阶段可以把数据集文件登记成 `Artifact`，也可以用 `meta` 临时塞入部分字段，但**不建议把四组数据正式导入当前六表模型**。这样会丢失语义，并使后续评价无法区分金标准和模型输出。

## 2. 当前六张表能存什么

| 表 | 当前字段与能力 | 实际限制 |
| --- | --- | --- |
| `projects` | `name/description/owner/status/created_at` | 项目名全库唯一；没有组织、访问策略、数据集或基线版本 |
| `artifacts` | `kind/name/path/version/content/meta` | 把逻辑制品、具体版本和细粒度记录混在一张表；无 hash、MIME、来源、许可、父子结构和生命周期 |
| `trace_links` | 整份 Artifact 间的 source/target、relation、confidence、文本 evidence | 不能连需求条目与代码类；无候选/金标准/确认状态，无链接版本、有效期、生成器和结构化证据 |
| `chat_messages` | role、content、字符串 evidence 列表 | evidence 只是字符串，不能外键到原文定位或工具运行 |
| `report_runs` | 类型、标题、focus、Markdown、高亮、风险 | 列表/读取接口只返回概要，不返回 Markdown、高亮和风险；没有报告对应的数据/模型/规则快照 |
| `audit_events` | operation、任意 JSON payload/result | 没有 `project_id`、actor、correlation/run ID 和不可变策略，难以做项目级审计 |

### 2.1 API 层的额外限制

- 没有文件上传、目录采集、数据集导入或解析接口；当前只能调用通用 `add_artifact`。
- `DatabaseWriteRequest.payload` 是无类型 `dict`，缺字段时在运行期报错，不能在 API 边界给出稳定的字段级校验。
- `artifact_row()` 只返回正文前 180 字，且完全不返回 `meta`；即使把标签塞进 `meta`，现有读取 API 也取不回来。
- `report_row()` 不返回报告正文、高亮和风险。
- `trace_links` 没有唯一约束，重复导入会生成重复边。
- 新增 Artifact/TraceLink 时没有业务层校验两端是否属于同一项目。
- 代码没有为 SQLite 显式启用 foreign key pragma；仅写 `ForeignKey(..., ondelete="CASCADE")` 不能保证当前 SQLite 运行时一定执行外键约束。
- 没有分页查询；当前实现先把全部记录载入内存，再截取 `limit`。

## 3. 四组数据的可存储映射

### 3.1 ARTA

数据包含需求文本、原文件，以及 8—10 类 smell 命中词。DS1 共有 985 条，另有可测试性和工具评价工作簿。

| 信息 | 当前能否存 | 说明 |
| --- | --- | --- |
| 整个 XLSX/ZIP 的路径 | 部分可以 | 可建一个 `Artifact(kind=dataset_file, path=...)`，但不能保存二进制内容、大小和 hash |
| 每条需求文本 | 勉强可以 | 每条建一个 Artifact，会把“数据记录”冒充“生命周期制品” |
| smell 命中词 | 只能塞 `meta` | 无类型约束，读取 API 又不返回 `meta` |
| 人工标签与 ARTA/Smella 预测 | 不可以 | 无 annotation、annotator、label source、model run |
| 训练/验证/测试拆分 | 不可以 | 无 dataset membership/split |

### 3.2 SAFA / Dronology

两个 JSON 含 16 棵追踪树及 hazard、requirement、design、code、acceptance test、environmental assumption 等节点。

| 信息 | 当前能否存 | 说明 |
| --- | --- | --- |
| 树节点作为 Artifact | 部分可以 | `kind/name/content/meta` 可容纳节点，但重复节点、树成员关系和节点版本没有规范表示 |
| 父子边作为 TraceLink | 部分可以 | 可存粗粒度方向边，但无边来源、状态和版本有效期 |
| V0/V1 比较 | 不可以 | 一个 Artifact 只有一个松散版本字符串，没有逻辑制品—版本拆分，也没有 supersedes/change set |
| commit/status/timestamp | 只能塞 `meta` | 无规范字段和查询能力 |
| 同一节点进入多棵安全树 | 不可以 | 无 collection membership 或 argument tree 结构 |

### 3.3 LiSSA SMOS

数据含 67 个 use case、100 个 class artifact 和 1,044 条需求—代码金标准链接。

| 信息 | 当前能否存 | 说明 |
| --- | --- | --- |
| Use case 与 class | 可以但粒度含混 | 可各建 Artifact；如果今后 class 下还有 method，就无法自然扩展 |
| 1,044 条链接 | 结构上可以 | 可建 TraceLink，但不能标记为 `ground_truth`，也不能保存数据集版本 |
| 模型候选和排名 | 不可以 | 无 candidate、rank、retriever、各路 score |
| 链接接受/拒绝/待审 | 不可以 | 无 status/review decision |
| 评价结果 | 不可以 | 无 analysis run、prediction、metric observation |

不能把金标准链接写成 `confidence=1.0` 来代替其来源语义。金标准是人工/数据集裁决，模型置信度是预测量，两者不是同一字段。

### 3.4 Irrelevant Requirements

数据含 621 条需求、actor、action 和 relevant/irrelevant 标签。

| 信息 | 当前能否存 | 说明 |
| --- | --- | --- |
| 需求正文 | 勉强可以 | 每条可建 Artifact |
| actor/action | 只能塞 `meta` | 无 claim/slot 模型 |
| relevance 标签 | 只能塞 `meta` | 无 annotation 和 task definition |
| 14 个项目/文件的归属 | 部分可以 | `project_id/path` 可近似，但会混淆本系统项目与外部数据集项目 |
| 类别不平衡与数据拆分 | 不可以 | 无 dataset statistics/split |

## 4. 最小扩展方案

在导入数据前，建议先补下面 8 组实体。它们是最小可用集合，不需要立即实现完整知识图谱。

| 新实体/改表 | 关键字段 | 首先解决什么 |
| --- | --- | --- |
| `datasets` | name, source_url, doi, license, task_schema | 区分研究数据集与业务项目 |
| `dataset_versions` | dataset_id, source_revision, downloaded_at, checksum, manifest | 固定可复现实验输入 |
| `dataset_files` | version_id, path, mime, size, hash, raw_uri | 保存文件级来源与完整性 |
| `artifact_versions` | artifact_id, dataset/source snapshot, version, hash, raw_uri | 拆开逻辑制品与具体版本 |
| `artifact_units` | version_id, parent_id, unit_type, locator, text, structured_data | 保存需求、章节、类、方法、测试步骤等最小分析单元 |
| `annotations` | unit/link target, task, label, value, annotator, source, adjudication | 保存 smell、relevance、人工标签和分歧 |
| `trace_candidates` | source_unit, target_unit, run, generator, rank, scores | 将检索候选与事实关系分离 |
| 扩展 `trace_links` | relation_type, status, provenance, decision_id, valid_from/to | 区分金标准、已确认、拒绝和多版本关系 |

随后再补：

- `analysis_runs`：数据、代码、规则、模型、prompt、环境和成本快照；
- `evidence`：原文定位、工具结果、执行输出和反证；
- `findings/review_decisions`：质量问题、人工接受/拒绝/豁免；
- `executions/metric_observations`：构建、测试、覆盖、变异与静态分析结果。

## 5. 建议导入顺序

1. 先实现 `datasets/dataset_versions/dataset_files`，把当前 `manifest.json` 导入为来源登记；
2. 拆出 `artifact_versions/artifact_units`；
3. 用 Irrelevant Requirements 验证 unit + annotation；
4. 用 LiSSA SMOS 验证 unit + ground-truth trace；
5. 用 SAFA 验证多版本、重复节点成员关系和边的有效期；
6. 最后导入 ARTA 的多列 smell 与评价结果，验证多标签 annotation 和 analysis run。

在完成前两步以前，只登记数据集文件，不向当前 `artifacts/trace_links` 批量灌入记录。
